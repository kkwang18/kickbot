# Progress

## What's done

**Environment verified end-to-end.** Confirmed Isaac Lab v2.3.0 install,
G1 assets (`isaaclab_assets.robots.unitree`), and GPU/rendering pipeline all
work on this RunPod box. Found and fixed a real infra bug along the way:
Isaac Sim's Vulkan renderer failed with `ERROR_INCOMPATIBLE_DRIVER` because
`libEGL.so.1` (and `libGLU.so.1`, `libXt.so.6`) were missing from the
container image — fixed via `apt-get install libegl1 libglu1-mesa libxt6`.
Ran a short PPO smoke test on the existing `Isaac-Velocity-Flat-G1-v0` task
to prove G1 spawns, streams its USD from Nucleus, and simulates correctly.
See `SETUP.md` for full details and the fresh-pod quick-start.

**Ported Isaac Lab's AMP task from the generic Humanoid-28 skeleton to G1.**
Isaac Lab ships a working AMP (Adversarial Motion Priors) implementation at
`isaaclab_tasks/direct/humanoid_amp/`, but it's hardcoded to a different,
generic 28-DOF humanoid asset — not G1. Ported it to `tasks/g1_amp/` in this
repo (registered externally as `Isaac-G1-AMP-Kick-v0`, no changes to the
vendored Isaac Lab source tree):

- Uses `G1_MINIMAL_CFG` (37 DOF, 44 bodies) — the same asset already
  validated by Isaac Lab's own `Isaac-Velocity-Flat-G1-v0` task.
- Observation/action space sizes recomputed for G1's actual DOF/body counts
  (99 / 37, vs. the original's 81 / 28), confirmed via runtime introspection
  rather than guessed.
- `reference_body` set to `pelvis` (G1's actual floating-base link) instead
  of the original's `"torso"`, which doesn't apply to G1's kinematic
  structure. Also fixed a latent bug in the original where the reset
  strategy hardcoded `"torso"` directly instead of reading `cfg.reference_body`.
- `key_body_names` mapped to G1's real hand/foot links
  (`{left,right}_palm_link`, `{left,right}_ankle_roll_link`).
- Registered via a `.pth` file in the conda env (auto-imports the task
  package at Python startup) rather than modifying vendored Isaac Lab code.

**Validated with a placeholder reference motion.** No real motion data
exists yet, so `motions/g1_placeholder.npz` is a synthetic "motion" — G1's
default standing pose held static for 10 frames — generated by
`scripts/gen_placeholder_motion.py`. Its only job is to exercise the AMP
plumbing (motion loader, reset strategy, discriminator observation shapes)
without depending on retargeting being solved yet. Ran a short skrl AMP
training smoke test against it: environment instantiates, motion loads,
policy/value/discriminator networks build correctly, 20 iterations complete
with zero NaN/crashes, checkpoints save. Also found and fixed a real skrl
2.1.0 config version-skew bug along the way (several `AMP_CFG` fields were
renamed/removed since Isaac Lab's shipped example yaml was written) — this
would have broken Isaac Lab's own bundled AMP example too, not just ours.

Net result: the AMP-on-G1 machinery is proven to work mechanically. Nothing
about it can currently produce a karate kick, or any specific behavior —
the reference motion is a static pose, not a real motion.

## What's next

The placeholder motion is the only thing standing between "AMP works on G1"
and "G1 imitates a real motion." Two reasonable next steps, not necessarily
in order:

1. **Retarget one simple existing mocap clip (e.g. an AMASS walk cycle) onto
   G1** and confirm AMP training actually converges to recognizable walking
   behavior. This validates the retargeting pipeline on an easy, well-behaved
   motion before spending effort on the harder case (see below). Lower risk,
   faster to debug if something's wrong with the retargeting math.
2. **Build the video → 3D pose → retargeted motion pipeline** for the actual
   karate-kick footage. This is expected to be the hardest, most
   time-consuming part of the whole project — video-to-3D-pose tools
   (WHAM, 4D-Humans) are weakest exactly on fast, dynamic, single-limb
   motions like a kick (occlusion, motion blur, foot-contact ambiguity), and
   SMPL-to-G1 retargeting is a real DOF/proportion mismatch problem, not a
   relabeling exercise (different joint layout, limb ratios, joint limits).

After a real reference motion exists (from either path), remaining work per
the original plan: assemble the full reward (AMP/tracking term + balance/
stability + domain randomization for mass/friction/motor strength/latency,
borrowing the randomization structure already present in Isaac Lab's G1
velocity-task configs), then train on flat terrain and iterate before
considering harder terrain or sim-to-real.
